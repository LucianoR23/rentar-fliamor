## 1. Project Overview

### Vision

RentAR Admin es un sistema de gestión de alquileres diseñado para el mercado argentino. Permite a uno o varios administradores gestionar unidades (departamentos, locales, terrenos, casas), contratos con actualización automática por ICL/IPC/monto fijo/porcentaje fijo, cobros mensuales, grupos de unidades con distribución de costos, y un registro completo de gastos. El sistema consume los índices oficiales argentinos (ICL vía BCRA, IPC vía INDEC/argly) en tiempo real para calcular actualizaciones de alquiler.

El sistema tiene dos roles: **superadmin** (acceso total: crear, editar, cargar, eliminar) y **viewer** (solo lectura). La interfaz usa el concepto visual "Precision Dark" — estética densa e informativa, similar a Linear o Vercel Dashboard, con toggle dark/light.

### Goals

- Centralizar la gestión de contratos de alquiler con cálculo automático de actualizaciones según normativa argentina
- Distribuir costos grupales (agua, luz, expensas) automáticamente según configuración por tipo de unidad
- Generar recibos de pago y reportes administrativos en PDF listos para enviar
- Emitir alertas proactivas de vencimientos y actualizaciones próximas

### Success Metrics

- Tiempo para registrar un pago < 30 segundos
- Cálculo de actualización de alquiler en < 2 segundos (con cache)
- 0 errores en generación de PDFs en producción

- `groups` 1→N `group_expenses`
- `files` N→1 cualquier entidad (por `entity_type` + `entity_id`)

// lib/rent-calculator.ts
export function calculateRentUpdate(params: {
  currentPrice: number
  updateType: 'icl' | 'ipc' | 'fixed_amount' | 'fixed_percentage'
  updateValue?: number    // para fixed_amount o fixed_percentage
  indexValue?: number     // valor del índice (anual %)
  frequencyMonths: number // cuántos meses abarca esta actualización
}): { newPrice: number; increase: number; increasePercent: number } {
  const { currentPrice, updateType, updateValue, indexValue, frequencyMonths } = params

  let newPrice: number

  if (updateType === 'icl' || updateType === 'ipc') {
    // indexValue es % anual (ej: 29.63)
    // Para frecuencia de N meses: proporcional
    const periodRate = (indexValue! / 100) * (frequencyMonths / 12)
    newPrice = currentPrice * (1 + periodRate)
  } else if (updateType === 'fixed_percentage') {
    newPrice = currentPrice * (1 + updateValue! / 100)
  } else {
    // fixed_amount
    newPrice = currentPrice + updateValue!
  }

  return {
    newPrice: Math.round(newPrice),
    increase: Math.round(newPrice - currentPrice),
    increasePercent: ((newPrice - currentPrice) / currentPrice) * 100,
  }
}

// Response:
// { newPrice: 350000, increase: 84672, increasePercent: 31.9, indexValue: 29.63 }

## 8. Authentication & Authorization

### Auth Flow

1. Usuario no autenticado → middleware redirige a `/sign-in`
2. Login via Supabase Auth (email/password) → Supabase maneja sesión con cookies HttpOnly
3. En primer login: `requireRole()` crea registro en tabla `users` con rol default `viewer` si no existe
4. Superadmin asigna roles desde `/dashboard/settings`

### Protected Routes

- Todas las rutas bajo `/(dashboard)/*` requieren auth — middleware.ts
- `/sign-in` es pública

```typescript
// src/lib/auth.ts
import { createClient } from './supabase/server'
import { db } from './db'
import { users } from './schema'
import { eq } from 'drizzle-orm'

export async function requireRole(role: 'superadmin' | 'viewer') {
  const supabase = createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) throw new Error('Unauthorized')

  let dbUser = await db.query.users.findFirst({ where: eq(users.supabaseId, user.id) })
  if (!dbUser) {
    // Primer login: crear registro
    const [created] = await db.insert(users).values({
      supabaseId: user.id,
      email: user.email!,
      name: user.user_metadata?.full_name ?? user.email!,
      role: 'viewer',
    }).returning()
    dbUser = created
  }

  if (role === 'superadmin' && dbUser.role !== 'superadmin') throw new Error('Forbidden')
  return dbUser
}

// En API routes:
// await requireRole('superadmin') — solo superadmin
// await requireRole('viewer')    — cualquiera autenticado
```

### Middleware

```typescript
// src/middleware.ts
import { createServerClient } from '@supabase/ssr'
import { NextRequest, NextResponse } from 'next/server'

export async function middleware(request: NextRequest) {
  let response = NextResponse.next({ request })

  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_DEFAULT_KEY!,
    {
      cookies: {
        getAll: () => request.cookies.getAll(),
        setAll: (cookiesToSet) => cookiesToSet.forEach(({ name, value, options }) => {
          request.cookies.set(name, value)
          response.cookies.set(name, value, options)
        }),
      },
    }
  )

  const { data: { user } } = await supabase.auth.getUser()
  const isDashboard = request.nextUrl.pathname.startsWith('/dashboard') ||
    (request.nextUrl.pathname.startsWith('/api') && !request.nextUrl.pathname.startsWith('/api/indices'))

  if (isDashboard && !user) {
    return NextResponse.redirect(new URL('/sign-in', request.url))
  }

  return response
}

export const config = { matcher: ['/((?!_next|.*\\..*).*)'] }
```

### Directory Structure

- Server Components por default: hacen queries directos a PostgreSQL via Drizzle

### Key Patterns
- `src/lib/auth.ts` → `requireRole('superadmin' | 'viewer')` se llama al inicio de cada API route y Server Action que muta datos
- `src/lib/db.ts` → único punto de acceso a PostgreSQL. NUNCA importar drizzle directamente en componentes

- `src/lib/rent-calculator.ts` → `calculateRentUpdate()` es la función core. Nunca duplicar lógica de cálculo fuera de esta función
- Archivos: el cliente obtiene presigned URL via `/api/files/upload`, sube directo a R2, luego confirma via `/api/files/confirm`

## 16. Reglas No Negociables

1. **TypeScript strict mode** — `noImplicitAny: true`, `strictNullChecks: true`. Cero `any`.
2. **`requireRole()` en toda mutation** — Sin excepción. Cualquier API route o Server Action que cree, edite o elimine datos debe llamar `requireRole('superadmin')` al inicio.
3. **Una sola fuente de verdad para cálculos** — `calculateRentUpdate()` y `calculateGroupExpenseDistribution()` son las únicas funciones que calculan alquiler y distribución de costos. Nada de lógica duplicada en componentes.
4. **Nunca floats para dinero** — Todos los montos en `decimal(12,2)` en DB. En JS, trabajar con `string` de Drizzle o convertir a `number` solo para display.
5. **Archivos solo via R2** — Nunca almacenar binarios en PostgreSQL. Nunca exponer `r2_key` al cliente.
6. **Índices externos siempre via cache** — `getICL()` y `getIPC()` de `src/lib/indices.ts` con Redis. Nunca fetch directo a `api.argly.com.ar` fuera de esas funciones.
7. **Un componente por archivo, máximo 300 líneas** — Si crece más, extraer sub-componentes.
8. **Viewer es read-only absoluto** — El role `viewer` no puede llegar a ninguna mutation ni por frontend ni por API directa. Validar en el servidor, no confiar en UI.
9. **Formateo consistente de montos** — Siempre usar `formatCurrency(amount, 'ARS')` de `utils.ts`. Nunca strings hardcodeados de `$`.
10. **No deploy sin variables de entorno completas** — El build debe fallar si faltan vars críticas. Usar `src/lib/env.ts` con validación zod de `process.env` al startup.
